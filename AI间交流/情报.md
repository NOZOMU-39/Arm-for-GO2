### IMU UART 实测与手册解析（2026-09-03，提出:IMU → 针对:IMU/Jetson/全体）
- 实物状态：HI12S2-MI1-000 本体 ×2 已到手（一只在测，USB/UART 直连 CHCenter 可读）；**Jetson 侧 CAN 收发器（SN65HVD230 类，T801 无板载收发器）与 USBCAN 未到货 → CAN 实测锁死**
- **UART 波特率实测定论**：115200→~142Hz、460800→~500Hz、**921600→~1000Hz（0x91 全量 82B 帧达成）**——波特率＝物理水管，只配输出频率不拉波特率永远 ~142Hz；本节取代选型条目「UART 最高 1000Hz」的无实测表述（旧条目保留历史）
- **型号能力定论：HI12S2 = IMU/VRU，无磁力计**（规格书型号表：S3 才有磁力计/AHRS）→ 只能用 6 轴模式：**yaw 上电=0 相对航向、无绝对航向**；室内＋电机磁场环境 9 轴本应慎用，6DoF 选型正确，但系统设计须知无绝对航向（瞬态扰动测量不受影响）
- **测量链时间戳定论**：0x91 帧内 system_time 仅 u32 ms（24h 回绕），1kHz 下粒度＝帧周期，**只够丢帧检测，帧级定序须靠接收端时钟**——统一时间戳方案不能依赖 IMU 帧内时标
- **yaw 跨协议语义不一致（坑）**：HI91/CANopen＝±180° 逆时针正；J1939 YAW 前 4B＝0~360° **顺时针正**——枪口端 UART＋基座端 CAN（J1939）混用必须归一化
- 坐标系可配置体系（非死的）：URFR 24 安装位/自定义三位码（用户 XYZ ← 传感器方向 ±X±Y±Z，右手系）、ENU/NWU 切换（欧拉序 312↔321 随变）、轴输出可独立反向、CONFIG ATT RST 校平/相对零点；**传感器轴 X/Y/Z 印外壳丝印＝唯一物理基准**，机械装法定后声明 URFR 码输出即归一化
- **CAN 帧预算修正（影响上文速率预算）**：CANopen 每周期 4~6 帧/IMU（加计/陀螺/欧拉/四元数分帧，int16 定点），J1939 请求-应答开销翻倍 → **双 IMU 1kHz 全量走 CAN 物理不可行（≈8k 帧/s > 1M 上限 ~7400/s），1kHz 高保真唯一通道＝UART 921600**；CANopen 陀螺 int16 上限 ±3276.7°/s < 本体 ±4000°/s，大角速度会溢出；CAN 各频率档实际能力待硬件实测
- canhost 官方工具已内置 SocketCAN 硬件时间戳＋JSONL 落盘＋寄存器读写＋固件更新（J1939 主线 SA 0x55）——Jetson 侧先复用不造轮子
- 未解问题：CHCenter log 2026-09-03 08:14 起（921600/1000Hz 时段）**每秒 1 次 ch checksum error**（帧长 76），候选＝①1Hz 周期污染源 ②89% 高占用下 USB 桥丢字节；对照实验（降波特率）未完成，**此问题不清 1kHz 数据可信度打折**

### 双 CH340 × USB HUB 在 Jetson 的识别与收流诊断定论（2026-09-06，提出:IMU → 针对:IMU/Jetson/全体）

- **背景**：新购无源 USB2.0 HUB（华升 214b:7260）＋两个 CH340 USB-TTL（用户自购第三方转接，IMU 官方评估转接为 CP2104，SDK `usb_uart_drivers` 仅 CP210x）接 HI12S2 ×2；前任测 Jetson 上「识别不到两个/识别到也不工作」。经本地文档研读＋Windows 对照＋Jetson 现场多轮受控实验闭环。
- **分层定论①：HUB 与 tegra-xusb 组合不兼容（「识别不到」主因）**。HUB 插 Jetson → 双 CH340 枚举风暴失败：`usb X: device descriptor read error -110`（超时）＋`device not accepting address -71`，tegra-xusb 重试风暴设备号暴涨至 100+、lsusb 卡死、时好时坏（偶发全成功并稳定 90s，但一路出现 `ch341-uart: failed to read modem status: -110` 半死）。**同一 HUB 与同一批设备在 Windows 上双插同时收流 = 996fps×2、CRC 0，完全正常**——HUB 硬件无碍，纯 Jetson 侧不兼容；结论：该 HUB 弃用于 Jetson（Windows 侧可留用）；Jetson 上如需扩展口应换有源/品牌 HUB。
- **分层定论②：ch341 驱动枚举后丢帧缺陷（「不能正常工作」主因，已获零成本解法）**。双 CH340 直插 Jetson（不经 HUB）识别稳定，但**每个 CH340 新枚举后 921600 收流固有丢 ~6.8%**：933fps、每 ~15ms 缺恰好 1 整帧（dt 空洞 2ms、CRC 全 0 = 整帧丢失非字节损坏）、无连续空洞；重启后干净环境依旧（排除运行时劣化）；单/双路、任意端口均复现。**往串口写 1 字节（0x00）后立即 999.9fps 完整无丢；拔插/重启后回丢帧态，再写再修复——三次可复现**，判定为 ch341 驱动在 tegra-xusb 上的 RX 调度缺陷，首次 TX 触发修复。**应用侧纪律：任何 Jetson 采集代码 open 串口后必须先 write 1 字节再读**（Windows 侧无此问题：同设备 996fps）。修复后验证基线：双 CH340 直插 30s 长测 999.9fps ×2、CRC 0/1。
- **分层定论③：板载 USB 口质量问题（次要，观察项）**。Jetson 板载 hub 端口 1-3.4 插两台不同 CH340 均出现过枚举失败/`modem status -110` 半死（时好时坏，重插/重启可恢复）；另一台设备在 port1 也出现过一次同款半死——疑似板载 USB 链路（端口/焊点/供电）间歇性电气劣化，建议固定使用 port1＋port3（现用组合 30s 双路 999.9fps 稳定），port4 避用；长期观察，若再发需查板卡 USB 硬件。
- **Windows 侧线索**：今日 CHCenter 日志 COM8 断开前每秒十几次 checksum error（基线约 20s 一次）——疑同链路劣化（当时设备经 HUB/换插），未深挖；HUB 在 Windows 双插实测正常。
- **工具留档**：帧间隔分析器 `IMU_HI12S2_MI1\tools\imu_dt.py`（stdlib，判断丢帧形态/验证收流完整性）；Jetson 现场诊断脚本在 /tmp/claude（重启即清）。
- 官方文档核对补充：HI12S2-MI1-000 功耗 240mW（3.2~5.5V）；出厂默认 115200/8N1、HI91@100Hz；手册附录 C 认可 921600↔1000Hz。
- **HUB 可用性补充（同日实测，与上条同会话）**：华升 214b HUB 并非全废——**PCAN(USBCAN)经 HUB 完全可用**：枚举稳定、can0 查询 5 电机 10ms/5ms 双档 100% 回复、RTT 1.3~2.7ms、berr 0/0；**冷启动自启验证通过**（PCAN 经 HUB 插着重启：can0.service/arm-stack.service 均 active、can0 UP@1M、tcp_gateway 8888 监听、电机 80 帧 100% 回复，can0.service 一次成功未触发 udev 兜底）。**HUB 定位：USBCAN/Nordic 等低速外设可用；CH340 类 FS 高保真串口（IMU）仍必须直插**。
- **ch341 丢帧真根因修正（提出:IMU → 针对:IMU/Jetson/全体，2026-09-08 配置二分实锤，推翻上方 09-06「写激活」定论与 HUB 弃用定论）**：①**丢帧根因 = termios lflag ECHO 残留非驱动缺陷**——Linux tty 默认 c_lflag 含 ECHO，采集代码 os.open 后仅部分清除（漏 ECHO/ECHOE/ECHOK）时 n_tty 将输入逐字节回显至 TX，921600 已占 USB 全速 ~89% 带宽，叠加回显周期溢出丢整帧（933fps/每 ~15ms 缺 1 帧/dt 空洞 2ms/CRC 0，与 09-06 观测形态全同）；配置二分实证 V1 部分清除=935fps 丢帧 → V2 补清 ECHO=999.5fps → lflag 全清=1000.0fps。**标准配置 `at[3]=0`（lflag 全清），open 即满速，09-06「写 1 字节激活、拔插复发、三次可复现」系治标偏方已废**；imu_dt.py 2026-09-08 版内置修复。②**旧无源华升 HUB 与 Jetson 实测兼容（推翻 09-06 弃用定论）**：同日满挂 5 设备（双 CH340+PCAN+Nordic+鼠标）枚举干净（无 -110/-71、设备号 22~26）、双路 1000.0fps×2；**用户新购有源 HUB 亦通过**（1000.1fps×2）。09-06 枚举风暴疑隐藏变量（当时 PCAN 8.15.2 缺陷驱动在场/插口位置），未留证，以实测为准。**部署形态修正：CH340 直插或经 HUB 均可用（新旧 HUB 皆可），板载口解放**。③**ch341 满速收流后 close 高频死锁（实锤，同日升级）**：921600 满速收流 ≥30s 后 close（含完全正常的收流-close 序列，无任何折腾）→ ch341 芯片死锁、后续 os.open 永久挂起（60s+ 不返回、无 dmesg、USB 层疑似存活但 UART 控制通道不响应）——**当日 4 次收流会话 3 次触发**；恢复=拔插或 sysfs 软重置（`echo 0/1 > /sys/bus/usb/devices/<1-3.x>/authorized`，~2s 重枚举）。采集栈设计约束：常驻收流避免频繁 close，或收尾用软重置代替 close，或 open 前 timeout 探测自动恢复。④验证基线更新：修复版双路 30s 长测 1000.0fps×2（30001±2 帧/路、mean 1.0000ms、大空洞≈0），超 09-06 的 999.9fps。⑤其余 09-06 定论不变：板载 port4（1-3.4）间歇坏避用、HUB 供 PCAN/Nordic 可用、ch341 与 tegra-xusb 拓扑无关性未涉。

## 七、安全决策（完整，2026-08-16）
### 总体原则
- 三线并行：结构、硬件、软件同时推进；第一版以控制实现复杂度低为准
- 无抱闸 → 断电坠落 → 物理兜底不可省略
- 动现有代码/硬件前必须经用户同意

### 结构线
- 加强优先级：①Go2 背板与 X8 连接（加厚衬板 5~8mm 铝合金、螺栓 M5×4 以上＋防松、背板加筋）②大臂根部法兰（增厚或径向筋、转接件整体化）③小臂/腕（壁厚/截面加大控重、避免细颈）④末端护罩（摄像头/激光笔/枪座一体）
- 机械零点：每关节一组"凸点＋刻线"（0° 参考位），做在连接件上不依赖电机型号；找零 SOP＝断电/失能→人工低速转至凸点对齐→设零（**V3 记 E0 机械零点档案——0x63/0x64 对旧款实测无效，见第八节，勿再按"V3 单发 0x64"操作**；V4 按 0x80→0x64→0x76）→记录档案；换新版 X8 沿用，档案版本＋1
- 限位两档：软限位（人工引导标定：转两端→记录→自动加裕度 max(5°, 行程×5%)）＋泡棉挡块（高密度聚氨酯 Shore 40~60A、行程两端、预压缩 3~5mm、结构胶＋压板）；金属硬限位列后续
- 安全姿态：收拢低势能＋末端有支撑

### 硬件线
- 供电分级与 12V 电池接管见第四节
- 急停接法与反馈见第四节
- ESP32 心跳看门狗：规格已交付，本期不落地（固件不动）

## 八、关键协议结论（实测/手册，勿轻易推翻）
- 两代均无使能环节：上电直接发闭环指令；0x80 关闭/0x81 停止
- V3.91（2026-08-20 终版实测定论）：0x20 仅索引 1/2，无多圈掉电保存；0x60/0x61/0x62/0x63/0x64 实测全部无效（写 ROM 类被固件砍掉）；**旧款 X8/X6-S2 = 转子侧单圈绝对值编码器 + 固件内部维护多圈角（0x92 可读，回复在 D1~4 int32 0.01°/LSB，会被 0xA8 增量漂移成 ±360N）**；**0xA4 = 多圈绝对角目标，固件按「目标−当前」差值直接执行**（非最短路径、非单圈相位）；上位机终版方案：0x92 轮询校准 rotDeg 到固件角 + **E0 标定存凸点固件角（含圈号，非相位——存相位发 0° 会偏 60°）** + 0xA4 发 R_t=E0+out2rot(deg)；12 条踩坑全记录见 电机上位机开发\README.md「问题 E」章节（**技术归档.md 已于 c02b0ef 并入 README，本处原引用为死链已更正**）；0x9C D6~7＝16 位编码器脉冲（相位源）；0xA1 力矩在 D4~5；0x79 读/写 ID 固定发 **0x300**、读回复 D6-D7＝回复 CAN 地址 0x240+编号，对拨杆设 ID 的旧款无效；**2026-08-25 补充：0x9C 相位最近邻校准在快速反转瞬间会取错 ±360N（采样间相位跳变>180°）→ 显示角虚跳 → 限幅越限误报（实测 X8 带负载转子 3 圈后出现）——0x92 轮询到位时 0x9C 相位仅作兜底，已修；用户确认修复后「连续按导致的报错可接受」（2026-08-25 用户结论）**
- V4.4（适用对象：X2-7 腕/末端 Yaw）：0x20 共 8 索引，索引 4＝多圈掉电保存（置 1，掉电前自动保存，重启生效，失能时写）；0x9C D6~7＝输出轴角度 int16；0xA1 力矩在 D2~3；0x64 设零必须 0x80→0x64→0x76 三步，单发无效
- **0x20 索引 6/7（V4 全系）= 位置运行最大正/负角度**（V4.0 起，2026-08-24 官方上位机交叉验证定论）：单位 **1°/LSB**（用户实测写 360 末端转子最高只能转 360°，官方上位机字段标 Deg）；**出厂默认 65535 = 未设限**（协议未说明此默认值，读回 65535 属正常勿当异常）；**仅失能状态才能保存 ROM**（手册 2.35.1 明文）——自研上位机写入已自动 0x80 失能前置；回显按 int32 补码原样（写 -180 回 4C FF FF FF）；**2026-08-24 真机验证：X6-40 写回 65535 后「±180 限位发 0° 停 +180°」异常消除、电机恢复正常**——证明 65535 写入真实生效（关闭固件限位）、±180 组合确实触发固件限位异常（机理未完全定论）；**需要限位时建议先小角度验证，65535 为安全默认**
- **0x94 单圈角度 = 转子侧相位**（2026-08-24 日志实证：0x9C=0° 时 0x94=334.87°，非输出轴角度），仅协议自测/手动读用；**V4 显示精度用 0x92**（多圈绝对角 int32 0.01°/LSB，与 0x9C 同基准，2026-08-22 快照实证 0x92≈0x9C）；0x01° 小数看面板/曲线、手动读 0x92 日志；**收发日志不刷轮询**（用户明确要求，日志是给人读的，0x9A/0x9C/0x92 轮询帧一律静默）；**控制回复/0x9C 日志角度显示 = 0.92 缓存优先**（0xA4 等回复角度字段手册为 1°/LSB 帧内无小数，轮询开启时日志角度显示 0x92 的 0.01° 值，与面板/曲线一致）；固件限位输入框默认 65535 与固件默认读数一致
- 官方上位机参考（Database\电机\，2026-08-24 入档）：**MC300 上位机**（适配 V2V3，Release\MC_300.exe）+ **MYACTUATOR V4.0 上位机**（适配 V4，界面字段 Max Positive Position(Deg)/Max Current(A)/Max Speed(RPM) 等）——联调对照、协议字段单位交叉验证用
