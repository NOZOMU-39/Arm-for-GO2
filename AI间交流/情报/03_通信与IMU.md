## 六、IMU 选型与通信速率预算（2026-08-16）

### IMU 选型（用户确认 2026-08-16）
- 厂商：HIPNUC 精浦科技，天猫旗舰店 hipnuc.tmall.com / 京东 mall.jd.com/index-16829568.html
- 用户确认：**两个 IMU 统一 HI12S2，串口+CAN 版本（MI1，UART+CAN 内置收发器）**；枪口端与基座端均为 HI12S2-MI1-000
- 关键性能（S2）：陀螺 ±4000°/s、加计 ±32g、20bit、3dB 带宽 80~400Hz、输出最高 1000Hz（UART/CAN）、零偏不稳定性 1.5°/h、加计 10ug；22×22×10mm、<8g、铝合金 CNC 外壳；抗振 ≤20g(58-600Hz)、抗冲击 2000g；供电 3.3~5.5V（内置 LDO）
- 接口/协议：CAN 125K/250K/500K/1M（默认 500K、CANopen、100Hz），支持二进制/CANopen/Modbus；UART 最高 1000Hz；支持外部触发同步（SYNC 延时 800µs）
- 开源友好：官方 GitHub `hipnuc/products`（协议库＋STM32/ROS/ROS2/Linux/MATLAB 例程，含 hipnuc_imu_can）；中文数据手册/指令手册公开
- 下单确认：MI1（UART+CAN）、6DoF 版、-000（Molex 接口）
- 排除记录：达妙 DM-IMU-L1（yaw 1h 零漂 12.686°，社区实测更差）；GY-H1（ICM42688+CAN 全开源但无零售渠道，备选自制）；北微 BW-IMU125（带宽 100Hz、量程 ±400°/s 不够）；维特 JY931（无 CAN）

### 无线链路与速率预算
- 现状（提出:固件 → 针对:固件/交互界面）：ESP32 v2.1.3 支持 TCP 8888 批帧推送（客户端协商 `0x0A13`）与可选 UDP 8889 订阅；**机械臂操作交互界面当前仅使用 TCP 批帧单源，已停用 UDP 订阅**（2026-08-26，避免双推挤占命令处理）。链路实测底线见第五节（接收 ≥750/s、发送 AP ~630/s，**真实接收上限未测出**）；CAN 1Mbps 物理上限约 7400 标准帧/s
- 分场景帧率预算：慢速位控全关节 200Hz ≈2.4k；射击阻尼瞬间（基座 yaw 1kHz＋枪口 IMU 1kHz＋其余 200Hz）≈5.1k；全关节 1kHz 双向＋2 IMU 1kHz＝12k（CAN 物理不可能，需 CAN FD 或双总线）
- 结论：算法框架最终需要**无线 ≥5k 帧/s、CAN 预算 ≤6k**；分频段设计（yaw 相关 1kHz，其余 200~500Hz）；无线侧批帧打包＋可选 UDP **理论可到 3~5k+ 帧/s（估算值，2026-09-01 用户确认未实测验证）**——v2.1.3 已落地批帧打包＋可选 UDP（2026-08-17 用户批准实施），实测接收上限受分析仪发送端限制仅验证 ≥750/s，**≥5k/s 需求与实测能力之间的差距仍未验证**

### IMU UART 实测与手册解析（2026-09-03，提出:IMU → 针对:IMU/Jetson/全体）
- 实物状态：HI12S2-MI1-000 本体 ×2 已到手（一只在测，USB/UART 直连 CHCenter 可读）；~~Jetson 侧 CAN 收发器与 USBCAN 未到货 → CAN 实测锁死~~**（2026-09-04 已解除：改用 PCAN-USB，can0@1M 已通、与 ZLG 双向零丢帧；板载 mttcan 已 blacklist，收发器方案作废）**。IMU 的 CAN 通路已具备，但 IMU CAN 实测尚未做
- **UART 波特率实测定论**：115200→~142Hz、460800→~500Hz、**921600→~1000Hz（0x91 全量 82B 帧达成）**——波特率＝物理水管，只配输出频率不拉波特率永远 ~142Hz；本节取代选型条目「UART 最高 1000Hz」的无实测表述（旧条目保留历史）
- **型号能力定论：HI12S2 = IMU/VRU，无磁力计**（规格书型号表：S3 才有磁力计/AHRS）→ 只能用 6 轴模式：**yaw 上电=0 相对航向、无绝对航向**；室内＋电机磁场环境 9 轴本应慎用，6DoF 选型正确，但系统设计须知无绝对航向（瞬态扰动测量不受影响）
- **测量链时间戳定论**：0x91 帧内 system_time 仅 u32 ms（24h 回绕），1kHz 下粒度＝帧周期，**只够丢帧检测，帧级定序须靠接收端时钟**——统一时间戳方案不能依赖 IMU 帧内时标
- **yaw 跨协议语义不一致（坑）**：HI91/CANopen＝±180° 逆时针正；J1939 YAW 前 4B＝0~360° **顺时针正**——枪口端 UART＋基座端 CAN（J1939）混用必须归一化
- 坐标系可配置体系（非死的）：URFR 24 安装位/自定义三位码（用户 XYZ ← 传感器方向 ±X±Y±Z，右手系）、ENU/NWU 切换（欧拉序 312↔321 随变）、轴输出可独立反向、CONFIG ATT RST 校平/相对零点；**传感器轴 X/Y/Z 印外壳丝印＝唯一物理基准**，机械装法定后声明 URFR 码输出即归一化
- **CAN 帧预算修正（影响上文速率预算）**：CANopen 每周期 4~6 帧/IMU（加计/陀螺/欧拉/四元数分帧，int16 定点），J1939 请求-应答开销翻倍 → **双 IMU 1kHz 全量走 CAN 物理不可行（≈8k 帧/s > 1M 上限 ~7400/s），1kHz 高保真唯一通道＝UART 921600**；CANopen 陀螺 int16 上限 ±3276.7°/s < 本体 ±4000°/s，大角速度会溢出；CAN 各频率档实际能力待硬件实测
- canhost 官方工具已内置 SocketCAN 硬件时间戳＋JSONL 落盘＋寄存器读写＋固件更新（J1939 主线 SA 0x55）——Jetson 侧先复用不造轮子
- 未解问题：CHCenter log 2026-09-03 08:14 起（921600/1000Hz 时段）**每秒 1 次 ch checksum error**（帧长 76），候选＝①1Hz 周期污染源 ②89% 高占用下 USB 桥丢字节；对照实验（降波特率）未完成，**此问题不清 1kHz 数据可信度打折**
- 资料本地化：`Database\IMU\`＝指令与编程手册（65 页）＋规格书（30 页）＋CHCenter（exe＋log）；PDF 中文提取须 pypdf（pdftotext 中文乱码）

### 双 CH340 × USB HUB 在 Jetson 的识别与收流诊断定论（2026-09-06，提出:IMU → 针对:IMU/Jetson/全体）

- **背景**：新购无源 USB2.0 HUB（华升 214b:7260）＋两个 CH340 USB-TTL（用户自购第三方转接，IMU 官方评估转接为 CP2104，SDK `usb_uart_drivers` 仅 CP210x）接 HI12S2 ×2；前任测 Jetson 上「识别不到两个/识别到也不工作」。经本地文档研读＋Windows 对照＋Jetson 现场多轮受控实验闭环。
- **分层定论①：HUB 与 tegra-xusb 组合不兼容（「识别不到」主因）**。HUB 插 Jetson → 双 CH340 枚举风暴失败：`usb X: device descriptor read error -110`（超时）＋`device not accepting address -71`，tegra-xusb 重试风暴设备号暴涨至 100+、lsusb 卡死、时好时坏（偶发全成功并稳定 90s，但一路出现 `ch341-uart: failed to read modem status: -110` 半死）。**同一 HUB 与同一批设备在 Windows 上双插同时收流 = 996fps×2、CRC 0，完全正常**——HUB 硬件无碍，纯 Jetson 侧不兼容；当时的「该 HUB 弃用于 Jetson」结论**已于 2026-11-06 覆写**（原文见 `99_变更记录.md`）：枚举失败后来定位为隐藏变量（当时 PCAN 8.15.2 缺陷驱动在场／插口位置）。**现口径：CH340 直插或经 HUB 皆可**，HUB 链已由 2026-11-06 双路 1000 Hz／30 min 长测验证。
- **分层定论②：ch341 驱动枚举后丢帧缺陷（「不能正常工作」主因，已获零成本解法）**。双 CH340 直插 Jetson（不经 HUB）识别稳定，但**每个 CH340 新枚举后 921600 收流固有丢 ~6.8%**：933fps、每 ~15ms 缺恰好 1 整帧（dt 空洞 2ms、CRC 全 0 = 整帧丢失非字节损坏）、无连续空洞；重启后干净环境依旧（排除运行时劣化）；单/双路、任意端口均复现。当时的「写 1 字节激活」偏方**已废**：真因于 2026-09-08 定位为 **termios lflag ECHO 残留**（非驱动缺陷），修法＝`at[3]=0`（lflag 全清），open 即满速，详见本册 2026-09-08 条①。修复后验证基线：双 CH340 直插 30s 长测 999.9fps ×2、CRC 0/1。
- **分层定论③：板载 USB 口质量问题（次要，观察项）**。Jetson 板载 hub 端口 1-3.4 插两台不同 CH340 均出现过枚举失败/`modem status -110` 半死（时好时坏，重插/重启可恢复）；另一台设备在 port1 也出现过一次同款半死——疑似板载 USB 链路（端口/焊点/供电）间歇性电气劣化，建议固定使用 port1＋port3（现用组合 30s 双路 999.9fps 稳定），port4 避用；长期观察，若再发需查板卡 USB 硬件。
- **Windows 侧线索**：今日 CHCenter 日志 COM8 断开前每秒十几次 checksum error（基线约 20s 一次）——疑同链路劣化（当时设备经 HUB/换插），未深挖；HUB 在 Windows 双插实测正常。
- **工具留档**：帧间隔分析器 `IMU_HI12S2_MI1\tools\imu_dt.py`（stdlib，判断丢帧形态/验证收流完整性）；Jetson 现场诊断脚本在 /tmp/claude（重启即清）。
- 官方文档核对补充：HI12S2-MI1-000 功耗 240mW（3.2~5.5V）；出厂默认 115200/8N1、HI91@100Hz；手册附录 C 认可 921600↔1000Hz。
- **HUB 可用性补充（同日实测，与上条同会话）**：华升 214b HUB 并非全废——**PCAN(USBCAN)经 HUB 完全可用**：枚举稳定、can0 查询 5 电机 10ms/5ms 双档 100% 回复、RTT 1.3~2.7ms、berr 0/0；**冷启动自启验证通过**（PCAN 经 HUB 插着重启：can0.service/arm-stack.service 均 active、can0 UP@1M、tcp_gateway 8888 监听、电机 80 帧 100% 回复，can0.service 一次成功未触发 udev 兜底）。**HUB 定位（2026-11-06 覆写）：USBCAN/Nordic 等低速外设可用；CH340 类 FS 高保真串口（IMU）经 HUB 亦可用**——「必须直插」已于 2026-09-08 推翻，2026-11-06 双路 1000 Hz／30 min 长测再次确认。
- **ch341 丢帧真根因修正（提出:IMU → 针对:IMU/Jetson/全体，2026-09-08 配置二分实锤，09-06「写激活」「HUB 弃用」两处旧定论已就地覆写（原文见 99 册））**：①**丢帧根因 = termios lflag ECHO 残留非驱动缺陷**——Linux tty 默认 c_lflag 含 ECHO，采集代码 os.open 后仅部分清除（漏 ECHO/ECHOE/ECHOK）时 n_tty 将输入逐字节回显至 TX，921600 已占 USB 全速 ~89% 带宽，叠加回显周期溢出丢整帧（933fps/每 ~15ms 缺 1 帧/dt 空洞 2ms/CRC 0，与 09-06 观测形态全同）；配置二分实证 V1 部分清除=935fps 丢帧 → V2 补清 ECHO=999.5fps → lflag 全清=1000.0fps。**标准配置 `at[3]=0`（lflag 全清），open 即满速，09-06「写 1 字节激活、拔插复发、三次可复现」系治标偏方已废**；imu_dt.py 2026-09-08 版内置修复。②**旧无源华升 HUB 与 Jetson 实测兼容（推翻 09-06 弃用定论）**：同日满挂 5 设备（双 CH340+PCAN+Nordic+鼠标）枚举干净（无 -110/-71、设备号 22~26）、双路 1000.0fps×2；**用户新购有源 HUB 亦通过**（1000.1fps×2）。09-06 枚举风暴疑隐藏变量（当时 PCAN 8.15.2 缺陷驱动在场/插口位置），未留证，以实测为准。**部署形态修正：CH340 直插或经 HUB 均可用（新旧 HUB 皆可），板载口解放**。③**ch341 满速收流后 close 高频死锁（实锤，同日升级）**：921600 满速收流 ≥30s 后 close（含完全正常的收流-close 序列，无任何折腾）→ ch341 芯片死锁、后续 os.open 永久挂起（60s+ 不返回、无 dmesg、USB 层疑似存活但 UART 控制通道不响应）——**当日 4 次收流会话 3 次触发**；**恢复手段 2026-11-06 覆写**（旧「拔插／sysfs authorized 软重置」降为末选，原文见 `99_变更记录.md`）：**reset 直系父 HUB**（`USBDEVFS_RESET` 打 HUB 的 usbfs 节点，~2 s 重枚举）；**禁止 reset CH340 芯片本身**；**恢复工具必须零 open**。触发概率**是概率性、非必现**（2026-11-06 30 min 满速跑完、收尾 reopen 双口 OK）。采集栈约束：常驻收流避免频繁 close，并提供 hub-first 自动恢复链。④验证基线更新：修复版双路 30s 长测 1000.0fps×2（30001±2 帧/路、mean 1.0000ms、大空洞≈0），超 09-06 的 999.9fps。⑤其余 09-06 定论不变：板载 port4（1-3.4）间歇坏避用、HUB 供 PCAN/Nordic 可用、ch341 与 tegra-xusb 拓扑无关性未涉。

### IMU 双路 1000 Hz 在 Jetson 的落事实测（2026-11-06，提出:IMU → 针对:IMU/Jetson/全体）

> 本节是**当前有效口径**。被它推翻的旧句已在原处就地覆写（见本册 2026-09-06／09-08 条内的「覆写」标注），被删掉的原文存 `99_变更记录.md`「2026-11-06 覆写记录」。

- **身份识别定论（取代「只能看哪个 USB 口被占用」）**：查询指令 `LOG VERSION`，回包含 `PNAME / BUILD / UUID / SN / APP_VER / BL_VER`。实测两台：`24B4EB573C480701`（**SN 为空串**）、`243173AE3CCD8701`（SN `12162630500043`）。**UUID 随模块走、与 USB 口无关**——一次 hub reset 后 `1-3.3.1`/`1-3.3.2` 与 `ttyUSB0`/`ttyUSB1` 的对应关系对调，两个 UUID 仍各跟各的模块。`/dev/serial/by-id` 不可用于区分（两颗 CH340 的 `ID_SERIAL` 完全相同），`by-path` 随插口变。→ 驱动按 UUID 派角色，花名册放配置文件；**认不出的设备照样出数据、只报 WARN**，绝不拒跑。
- **双路 30 min 长期基线（本季唯一长期基线，取代 2026-09-08 的 30 s 基线）**：基座拓扑 `usb1 → 1-3(Realtek 0bda:5489) → 1-3.3(Genesys 05e3:0610) → 1-3.3.1 / 1-3.3.2 (CH340)`；1800 s 两路各 **1,800,040 帧＝1000.022 fps**、CRC 坏帧 **0**、`sys_time` 相邻步长恒 1 ms（**零丢帧**，手册认可判据）、收尾 reopen 双口 OK。JSON 落在 Jetson `~/imu_probe/baseline/soak30m.json`。
- **两条新纪律（2026-11-06，优先级高于本册旧条目的恢复做法）**：①**永远不要 reset CH340 芯片本身**——无效（ioctl 超时）且会把设备整条打下 USB 总线（`/dev/ttyUSB*` 直接消失），把小问题变成大问题；②**恢复工具必须零 open**——楔死口在 sysfs 里照样显示「ch341 已绑定」，用 open 去「验证健康」会把刚救回来的口再次打死（实测：reset 成功 → probe 全 OK → 紧接着业务 open 立刻 `OSError: [Errno 5] Input/output error`）。
- **恢复链定案（已落地）**：L1 现有 tty 的 sysfs 祖先 HUB 由深到浅 reset → L2 拓扑缓存里的 HUB（设备掉出总线后唯一线索）→ L3 现场兜底（子设备全 CH340 且**非空**的 HUB；空 HUB 会让 `all([])` 恒真而被误选）→ L4 authorized 软重置（**默认关**，HUB 下有 clear tt error -71 风暴史）→ L5 人工。健康期由采集进程自动写 `~/imu_probe/topology.json`（当前 `['1-3.3','1-3']`）。
- **口径：波特率是派生量**——先定 `sample_rate_hz = 1000`；HI12S2 要达成 1000 Hz 才**必须**把 UART 开到 921600。配置与核心层不出现「921600」这个事实，换厂家时不被写死。
- **装点定案（用户 2026-11-06 定）：基座端 IMU 装 X8 定子侧，绝不装转子**——转子随 yaw 转，会把 yaw 角速度污染进全部测量；基座端与末端端均按 IMU 默认 y 轴对齐基座 x 轴、z 轴竖直向上。
- **工具留档**：`IMU_HI12S2_MI1\tools\baseline\` ＝ `hi12_link.py`（链路层：CRC-16/XMODEM、0x91 解析、termios **lflag 全清**）、`baseline_run.py`（长期基线长测＋JSON）、`ch340_recover.py`（hub-first 恢复，零 open）。
