## 八、关键协议结论（实测/手册，勿轻易推翻）
- 两代均无使能环节：上电直接发闭环指令；0x80 关闭/0x81 停止
- V3.91（2026-08-20 终版实测定论）：0x20 仅索引 1/2，无多圈掉电保存；0x60/0x61/0x62/0x63/0x64 实测全部无效（写 ROM 类被固件砍掉）；**旧款 X8/X6-S2 = 转子侧单圈绝对值编码器 + 固件内部维护多圈角（0x92 可读，回复在 D1~4 int32 0.01°/LSB，会被 0xA8 增量漂移成 ±360N）**；**0xA4 = 多圈绝对角目标，固件按「目标−当前」差值直接执行**（非最短路径、非单圈相位）；上位机终版方案：0x92 轮询校准 rotDeg 到固件角 + **E0 标定存凸点固件角（含圈号，非相位——存相位发 0° 会偏 60°）** + 0xA4 发 R_t=E0+out2rot(deg)；12 条踩坑全记录见 电机上位机开发\README.md「问题 E」章节（**技术归档.md 已于 c02b0ef 并入 README，本处原引用为死链已更正**）；0x9C D6~7＝16 位编码器脉冲（相位源）；0xA1 力矩在 D4~5；0x79 读/写 ID 固定发 **0x300**、读回复 D6-D7＝回复 CAN 地址 0x240+编号，对拨杆设 ID 的旧款无效；**2026-08-25 补充：0x9C 相位最近邻校准在快速反转瞬间会取错 ±360N（采样间相位跳变>180°）→ 显示角虚跳 → 限幅越限误报（实测 X8 带负载转子 3 圈后出现）——0x92 轮询到位时 0x9C 相位仅作兜底，已修；用户确认修复后「连续按导致的报错可接受」（2026-08-25 用户结论）**
- V4.4（适用对象：X2-7 腕/末端 Yaw）：0x20 共 8 索引，索引 4＝多圈掉电保存（置 1，掉电前自动保存，重启生效，失能时写）；0x9C D6~7＝输出轴角度 int16；0xA1 力矩在 D2~3；0x64 设零必须 0x80→0x64→0x76 三步，单发无效
- **0x20 索引 6/7（V4 全系）= 位置运行最大正/负角度**（V4.0 起，2026-08-24 官方上位机交叉验证定论）：单位 **1°/LSB**（用户实测写 360 末端转子最高只能转 360°，官方上位机字段标 Deg）；**出厂默认 65535 = 未设限**（协议未说明此默认值，读回 65535 属正常勿当异常）；**仅失能状态才能保存 ROM**（手册 2.35.1 明文）——自研上位机写入已自动 0x80 失能前置；回显按 int32 补码原样（写 -180 回 4C FF FF FF）；**2026-08-24 真机验证：X6-40 写回 65535 后「±180 限位发 0° 停 +180°」异常消除、电机恢复正常**——证明 65535 写入真实生效（关闭固件限位）、±180 组合确实触发固件限位异常（机理未完全定论）；**需要限位时建议先小角度验证，65535 为安全默认**
- **0x94 单圈角度 = 转子侧相位**（2026-08-24 日志实证：0x9C=0° 时 0x94=334.87°，非输出轴角度），仅协议自测/手动读用；**V4 显示精度用 0x92**（多圈绝对角 int32 0.01°/LSB，与 0x9C 同基准，2026-08-22 快照实证 0x92≈0x9C）；0x01° 小数看面板/曲线、手动读 0x92 日志；**收发日志不刷轮询**（用户明确要求，日志是给人读的，0x9A/0x9C/0x92 轮询帧一律静默）；**控制回复/0x9C 日志角度显示 = 0.92 缓存优先**（0xA4 等回复角度字段手册为 1°/LSB 帧内无小数，轮询开启时日志角度显示 0x92 的 0.01° 值，与面板/曲线一致）；固件限位输入框默认 65535 与固件默认读数一致

- **0x9D 回复布局两代同（提出:Jetson → 针对:交互界面/全体，2026-09-05 真机+手册实证修复）**：D1=**温度**（uint8，1℃/LSB），A/B/C 相电流 int16（0.01A/LSB）分别在 **D2-3/D4-5/D6-7**（V3.9 与 V4.4 手册原文一致，手册示例即含 ±30A 级电流）。旧实现（JS 与 arm_protocol 同源）按 i16(D1/D3/D5) 解析把温度吞进 A 相低字节 → 静止读数伪影为 -4~-27A 级（真机 ID3 曾显示 -27.92A）。**已修**：交互界面 index.html 与 `arm_protocol/parse.py` 同步（values 增 temp 字段、偏移 +1），Node 52/52 + pytest 5213 + golden 补真机样例（V4.4 手册乱码提取注意：中文 PDF 提取须 pypdf）。此 bug 系 JS 版 0x9D 从未真机验证、黄金对拍只保证双实现一致所致——教训：协议字段布局须以手册+真机双重实证。

- **来源标注**：本模块协议/角度/限位经验全部继承自上位机（第八节，来源已注明），本模块新增结论（无线节奏/多电机轮询/设零点重写等）在下方单独列出，均带「提出:交互界面」标注
- **技术路线（强依赖其他模块，同步进行）**：与 `电机上位机开发\` 同源——32 位 Python 3.12 + pywebview + 单文件 index.html；协议核心（组帧/解析/角度模型/限幅链）从上位机 index.html 移植，不重新发明；注册表独立（`机械臂注册表.json`，临时参数），可经文件选择器一次性导入上位机注册表（不联动）
- **无线通信（复用 ESP32 v2.1.3）**：交互界面命令与反馈均走 TCP 8888（`wifi_can_client.py` 原样复制当库用，批帧协商 `0x0A13`）；2026-08-26 起停用 UDP 8889 双推，避免反馈挤占命令处理；⚠️ 不可用 `client.monitor()`（持锁 0.5s 阻塞发送），当前 TCP 读线程采用批量读取与流式解析；不做自动重连（防半连通误判）；host 留空走四级自动发现
- **功能**：USB/无线双通道连接（波特率默认 1000）、多电机实时曲线网格（角度/速度/电流，双击放大、参数全局开关、自适应/固定量程）、位置控制（绝对/相对/键盘 ↑↓ 按住连续松手停，唯一控制方法）、每电机设零点（当前位置标定为输入值：V3 记 E0 档案、V4 三步设零+显示偏移 E4）、软件限幅（最大/最小角）安全链（发送前校验+运行中越限先停再报警+越限锁定）、扫描一致性检查（只警告不动作）、三层日志（帧行附操作名/JS 摘要/界面）
- **界面约定（用户 2026-08-26 规定）**：提示一律 hover 悬浮式（data-tip），有范围/默认值的必须写明完整范围；界面不显示任何指令名/指令号（文件日志 tx note 保留供 AI 排查）
- **状态速览（提出:交互界面 → 针对:交互界面）**：V1.0 完成、设零二次修复（03eccf0）、Node 52/52、已打包——修复细节见下两条 08-26 排查结论；A 段验收状态与遗留项见「十一」节（2026-09-05 起不再在此重复状态）。
- **2026-08-26 真机排查结论（本日多次实测定论）**：
  - **无线丢帧根因 = 发送节奏（版本引入）**：06:49 提交 173e22b 把发送从库 `send_can`（持锁）改为**直接 `conn.sendall` 无锁** → 轮询命令背靠背快速连发 → 总线瞬时突发 → **9A/9C 类回复在总线上损坏被 ESP32 TWAI CRC 拒收**。证据链：①30ms 帧间隔丢 60-87%、**60ms 帧间隔 X6 9A/9C 恢复 93%**（probe 实测）②USBCAN 旁听：ESP32 命令 100% 在总线、X6 回复 9A/9C 在总线就缺 50%、捕获**帧数据错位帧**（0x242 00 00 00 9A 1B 00 00 E9 = X6 9A 回复右移 3 字节，位时序漂移证据）③ESP32 内部 RX 计数 0-3/6（发 6 帧轮询）④06:43 正常 → 06:57 新版 exe 丢帧开始，分界 = 173e22b 打包。**已修**：pollAll 每帧间 sleep(60) + polling 忙标志防并发（git a8e866a/3e07caf）；轮询默认 500ms（d967155）
  - **遗留 A（X8 9C 批次性丢失 ~47%）**：与帧间隔无关（60ms 仍丢），批次性时好时坏 → 疑似 **X8 侧硬件**（CAN 线缆/端子接触、收发器），软件已尽力，需用户检查 X8 CAN 线
  - **遗留 B（ESP32 固件 bug）**：单帧模式**重复推送 4.4 倍**（probe 收到 320 帧/发送 72 帧）；密集帧下接收/推送异常。固件 v2.1.3 Custom 有缺陷但 60ms 节奏可缓解，未改固件
  - **电机卡片区空白根因（已修，dc72fbe/21e90c7）**：V3 9C 相位路径 `v3PosDual` 在 lastEnc 未就绪时返回 **null** → `lastAngle[id]=null` → 界面 `!== undefined` 判空失效（null ≠ undefined）→ `null.toFixed()` 抛异常 → renderMotorCards 中断 → 卡片区空白；每秒刷新同步中断致兜底不执行。修法：治本（null 不写入 lastAngle）+ 治标（全部 lastAngle 使用点改 `typeof === "number"` 判空，9 处）。**新增 JS 异常/未处理 Promise 落盘诊断**（window.onerror → log_line，3d52afb），日志可见 `[JS异常]` 行

  - **设为零点重写完成（提出:交互界面 → 针对:交互界面，2026-08-26）**：用户实测「一瞬间归零随后恢复」（交接文档「确认后无效果」系更早观察，两现象并存）→ 根因：V4 三步 0x80→0x64→0x76 **背靠背连发零间隔**——0x64 写 ROM 是慢操作，被 0x76 复位打断 → 新零点不进 ROM → 复位后 0x92 读回旧值覆盖前端强制 lastAngle=0（「一瞬间归零」= 前端强制，「恢复」= 0x64 未生效）。重写内容：①三步加节奏 0x80→sleep(300)→0x64→sleep(1000)→0x76→sleep(3000) 等复位完成（⚠️ 此节奏为初版，**二次修复已改为 500/1000/10000ms，以二次修复为准**） ②每步结果落盘（setZeroNow 入口/确认/三步/完成各行）③V3 设零前校验 lastAngleSrc==="0x92"（0x92 未到位时 rotDeg 由 0x9C 相位积分，防 E0 记错圈 ±360N）④showConfirm 并发防御（confirmResolve 单变量被并发覆盖致 Promise 永挂→先作废旧确认再弹新窗）。回归 52/52，已打包
  - **设为零点真机实测与二次修复（提出:交互界面 → 针对:交互界面，2026-08-26，日志 103844）**：三次实测 1 成功 2 失败（10:41:03/10:44:17 失败、10:41:48 成功）。**失败特征 = 0x76 后无复位空窗**（电机未复位，0x92 恒读旧值 10.53°/-90.06°）；**成功特征 = 0x76 后约 10.5s 空窗**（10:42:00 起 0x92=0.00°）。二次根因 = **setZeroNow 执行期间 pollAll 并发轮询**——命令帧 0x80/0x64/0x76 与轮询 9A/9C/92 挤入 TCP→CAN 队列 → 总线背靠背突发（173e22b 根因再现）→ 0x76 偶发损坏丢失（发送成功≠执行成功）。已修：设零确认后置 **pollPaused 暂停轮询**（try/finally 恢复，三步命令独占总线节奏）+ 0x80→0x64 间隔 300→500ms（失能稳定）+ 0x76 后等待 3→10s（对齐实测复位耗时）。**验证方法**：设零后 0x92 应出现 ≥10s 无回复空窗再归 0；无空窗 = 0x76 未执行（失败）
  - **无线链路三现象实锤 + 优化建议（提出:交互界面 → 针对:固件，2026-08-26，请 ESP32 无线模块 AI 接手优化）**：①**单帧重复推送实锤**：同一 0x92 帧（0x242 92 00 00 00 1D 04 00 00）以 350~600ms 间隔重复推送 8+ 次（遗留 B 复现）——客户端 200ms 去重窗口挡不住（重复间隔 >200ms），界面重复处理；建议 ESP32 修复单帧重复推送或推送帧加序号 ②**复位命令后滞留帧**：0x76 复位命令发出 228ms 内仍收到复位前旧读数（ESP32 推送队列/UDP 缓冲滞留）——界面无法区分复位前/后数据；建议复位类命令后 ESP32 清空推送队列，或客户端按命令时序过滤 ③**无回复命令偶发丢失**：0x80/0x64/0x76 无回复确认，0x76 实测 2/3 偶发未执行（客户端已用「设零期间暂停轮询」缓解，治本需固件侧：命令与轮询帧分优先级/节奏，或批帧协商通道内加命令回执）
